# incus-support

Adds the guest side of the [Incus](https://linuxcontainers.org/incus/)
agent to an image converted by contemper, so a VM booted from the disk
under Incus runs the agent (`incus exec`, `incus file`, the guest's
state in `incus list`, and so on). The agent itself is not in the image:
Incus attaches it to every VM, and this image only adds what copies it
into the guest and starts it.

```sh
contemper convert --support ghcr.io/contemper-project/incus-support:v1 ...
```

## What it adds

The layout follows what [distrobuilder](https://github.com/lxc/distrobuilder)
installs when it builds Incus VM images (its `incus-agent` generator), so a
converted image looks like an official one. Each variant adds the
integration for one init system, including its own copy of the setup
script, which mounts the share Incus attaches (9p tag `config`, or the
CD-ROM), copies its contents into a tmpfs at `/run/incus_agent` and fixes
ownership. The base image has no files: it only carries the annotations
that select the variant. Nothing runs on a non-Incus host: the same disk
boots under plain QEMU without the agent.

| Image | Added files |
| --- | --- |
| `incus-support` (base) | none, only annotations |
| `incus-support-systemd` | `/usr/lib/systemd/incus-agent-setup`, `/usr/lib/systemd/system/incus-agent.service` and `/usr/lib/udev/rules.d/99-incus-agent.rules`. The unit is not enabled; the udev rule starts it when `/dev/virtio-ports/org.linuxcontainers.incus` appears |
| `incus-support-openrc` | `/usr/local/bin/incus-agent-setup` and two services, `/etc/init.d/incus-agent-setup` (copies the agent into `/run/incus_agent`) and `/etc/init.d/incus-agent` (runs it, after the setup service), both enabled through symlinks in `/etc/runlevels/default/` |

The files go under `/usr/lib` and `/usr/local`, not `/lib`: the layers are
static, `/lib` is a symlink to `/usr/lib` on merged-`/usr` images, and
systemd and udev read `/usr/lib` on split-`/usr` ones too.

### Where the files come from

The setup script, the systemd unit and the udev rule are the Incus
project's own files, generated by `hack/sync-incus-agent.sh` from the Incus
release pinned in `incus-agent.pin` (tag and commit) with a header naming
their origin; the only change is upstream's `TARGET` placeholder resolved
to `/usr/lib`. A CI check fails if they differ from what the script
produces. Renovate proposes new Incus releases by changing the pin; the
files are then regenerated by running `hack/sync-incus-agent.sh` and
committing the result. See [NOTICE](../../NOTICE).

The two OpenRC services are written for this image, modelled on
distrobuilder's, with these differences:

- distrobuilder requires `/dev/virtio-ports/` for the setup service, which
  makes it fail on a VM that is not run by Incus. Here the setup service
  loads `virtio_console`, looks for the Incus virtio port by name in
  `/sys/class/virtio-ports` and, when there is none, skips with a one-line
  message, without delay and without failing. When there is one, it waits
  up to 10 seconds for the `/dev/virtio-ports/org.linuxcontainers.incus`
  link and fails with a message if it never appears.
- distrobuilder requires `/run/incus_agent` for the agent service. Here the
  agent service skips cleanly, also on stop and status, when the agent was
  not copied there.
- The udev rule is installed with mode 0644, where distrobuilder uses 0400.

## Variants

The base image has one branch, `init-system`:

| Variant | Applies when the image being converted has |
| --- | --- |
| `systemd` | `/usr/lib/systemd/systemd` |
| `openrc` | `/sbin/openrc` |

There is no default: converting an image with neither fails and names the
branch, rather than silently adding an agent that nothing starts. An
image with both is rejected as ambiguous.

## What the image being converted needs

The image is not checked for these:

- Kernel support for 9p and virtio (`9p`, `9pnet_virtio`), for
  `virtio_console` (the channel the agent uses) and for vsock
  (`vmw_vsock_virtio_transport`); `iso9660` as well if the CD-ROM
  fallback is used.
- A device manager (udev, eudev or mdev) that creates the
  `/dev/virtio-ports/*` symlinks, and loads these modules when the
  devices appear.
- `mount`, `cp`, `chown`, `umount`, `mkdir` and `rmdir` (busybox is fine). `modprobe`,
  `eject` and `restorecon` are used when present.

Cloud-init is not configured by this image. Ordering relative to
cloud-init differs by init system: under systemd the unit starts before
cloud-init's units (`Before=`). OpenRC orders services only within a
runlevel, and the agent is in the default runlevel, so on a distribution
that runs cloud-init in an earlier runlevel (Alpine runs `cloud-init-local`
in the boot runlevel) the agent starts after it.

## What `v1` promises

The major version is the interface to contemper, not the Incus version.
Within `v1` these stay as they are:

- the image names `incus-support`, `incus-support-systemd` and
  `incus-support-openrc`;
- the `init-system` branch with the variants `systemd` and `openrc` and
  their predicates above, and no other annotations contemper reads;
- the paths listed above.

Releases within `v1` may change the contents of the files, for example to
follow the upstream agent loader. A change to the interface above is a
new major version.
